# Build and test

How to build and test each part of Helm. Read the row for the part you change.

| Part | Build | Test |
|---|---|---|
| Rust host | `cargo build --workspace` | `cargo test --workspace` (+ `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`). After changing a type in `host/crates/chats/src/types.rs`, regenerate the UI bindings: `HELM_UPDATE_BINDINGS=1 cargo test -p helm-chats bindings_are_current` |
| UI | `npm run build -w ui`; to look at it without Tauri: `npx vite --port <free port>` in `ui/` opens against the dev fake host (`?seed=250` preloads a long chat; prompts containing "approve", "question", "plan" or "long" script those cards). Stable e2e hooks: `ui/TESTIDS.md` | `npm test -w ui` (+ `npm run typecheck -w ui`) |
| Tauri app (dev run) | `npm run dev` (Vite on 127.0.0.1:1420 + `cargo run`); production-CSP debug exe: `npm run build:debug` → `target/debug/helm.exe`; set `HELM_PROFILE_DIR` to a scratch folder to keep `%LOCALAPPDATA%\Helm` untouched | — |
| Worker + fakes | none: Node runs the TypeScript directly | `npm test` in `worker/` and in `fakes/`; live smoke (spends plan usage, once per checkpoint): `HELM_LIVE_CLAUDE=1 npm run test:live` in `worker/`. Chats on a local model use `fakes/local-model/` (one fake server for the Messages route and both servers' control routes, on an ephemeral port); a test never contacts a real model server |
| Side panel (host `helm-panel`, `ui/src/panel`, `ui/src/markdown`) | part of the Rust host and UI builds | `cargo test -p helm-panel` (staging tests need git on `PATH`); `node --test "src/panel/**/*.test.ts" "src/markdown/*.test.ts"` in `ui/`; e2e `checks/e2e/w3-panel.e2e.ts`. `HELM_TEST_OBSIDIAN_CONFIG=<obsidian.json>` (debug builds only) points the vault list at a test registry |
| End-to-end (fake claude) | `npm run build:debug` first (the check drives `target/debug/helm.exe`) | `npm run e2e -w checks`: E1–E8 over WebView2's DevTools port with playwright-core, scratch profile, `HELM_TEST_CLAUDE`; not part of `npm test`. `HELM_E2E_OUT=<dir>` keeps screenshots, `HELM_E2E_KEEP=1` the profile. The app window opens off-screen and unfocused by default (the debug build's `HELM_TEST_WINDOW=background`, which release builds ignore), so a run never takes over your screen; `HELM_E2E_SHOW=1` opens it normally, to watch a check |
| Hub (`hub/`, its own Cargo workspace, not in `--workspace`) + relay (`host/crates/relay`, `fakes/telegram`) | `cd hub && cargo build`; image: `docker build -t helm-hub:latest .` in `hub/` (built on the server that runs it; the dev machine needs no Docker) | `cd hub && cargo test` (+ `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`); `cargo test -p helm-relay`; `node --test "telegram/*.test.ts"` in `fakes/`; e2e `checks/e2e/w7-relay.e2e.ts` (needs `npm run build:debug` and `cargo build` in `hub/`); details in `hub/README.md` |
| Host tools + consent (`host/crates/{hosttools,consent}`, `worker/src/hosttools`, `ui/src/hosttools`) | as the Rust host and UI rows | `cargo test -p helm-hosttools -p helm-consent`; `node --test test/hosttools-*.test.ts` in `worker/`; `node --test src/hosttools/*.test.ts` in `ui/`; e2e `checks/e2e/w4-hosttools.e2e.ts`; live (spends plan usage) `HELM_LIVE_CLAUDE=1 HELM_LIVE_MCP_JSON=<a .mcp.json with the servers named in the check's header> npm run live -w checks` (`w4.live.ts`; the hub part needs `HELM_LIVE_HUB_URL` and `HELM_LIVE_HUB_TOKEN`). A new host tool's name goes in `host/crates/hosttools/reserved.json`, in `host/crates/hosttools/src/surface.rs` (its group, and whether it is in every chat's own list) and in the relay gate's table; the tool-surface baseline in `host/app/src/registrations.rs` pins the list, and its budget test caps what a chat's own tool list costs. Families of tools are merged into one tool with an `action` argument in `surface.rs`; `HELM_PRINT_BUDGET=1 cargo test -p helm-app a_chats_own_tool_list -- --nocapture` prints the sizes. What a fresh chat's first request is made of: `node checks/context-budget/measure.mjs <a Claude Code session log>` |
| MCP client (`host/crates/mcp`, `worker/src/mcp`, `fakes/mcp-server`, `ui/src/settings/mcp`) | none beyond the Rust host and UI rows | `cargo test -p helm-mcp`; `node --test test/mcp-*.test.ts` in `worker/` (fake MCP server, redaction, 10 servers, the connect-time address rule); `node --test src/settings/mcp/*.test.ts` in `ui/`; Settings → MCP end to end: `checks/e2e/w4-mcp.e2e.ts` |
| Plan usage + item links (`host/crates/{usage,itemlinks}`, `helpers/usage`, `worker/src/usage`, `ui/src/{usage,itemlinks,settings/usage}`) | as the Rust host and UI rows | `cargo test -p helm-usage -p helm-itemlinks`; `npm test -w helpers`; `node --test test/usage-*.test.ts` in `worker/`; `node --test src/usage/*.test.ts src/itemlinks/*.test.ts` in `ui/`; e2e `checks/e2e/w4-usage.e2e.ts`; live (reads real usage from the binary, sends no prompt) `HELM_LIVE_CLAUDE=1 node --test e2e/w4-usage.live.ts` in `checks/` |
| Schedules + AFK + governor (`host/crates/{schedules,afk,governor}`, `ui/src/{schedules,settings/schedules,afk}`) | as the Rust host and UI rows | `cargo test -p helm-schedules -p helm-afk -p helm-governor` (regenerate the schedules bindings with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-schedules bindings_are_current`); `node --test src/schedules/*.test.ts src/afk/*.test.ts` in `ui/`; e2e `checks/e2e/w7-schedules.e2e.ts` and `checks/e2e/w7-afk.e2e.ts`. AFK and governor settings live in each crate's own table, not in preferences (their classes are in `host/crates/core/src/db/tables.rs`). Scheduled prompts are sent with `helm_chats::submit::host_send` (origin `schedule`, gated), never the `chat_send` op |
| Workflow + orchestrator (`host/crates/workflow`, `fakes/standup-writes`) | as the Rust host row | `cargo test -p helm-workflow`; after changing a type in `host/crates/workflow/src/types.rs`, regenerate `ui/src/api/generated/workflow/` with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-workflow bindings_are_current`; e2e `checks/e2e/w6-workflow*.e2e.ts` |
| Gatekeeper (`host/crates/gatekeeper`, `helpers/gatekeeper`, `ui/src/gatekeeper`) | as the Rust host and UI rows | `cargo test -p helm-gatekeeper` (regenerate the gatekeeper bindings with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-gatekeeper bindings_are_current`); `node --test "gatekeeper/**/*.test.ts"` in `helpers/` (or `npm test -w helpers` for all helpers); e2e `checks/e2e/gatekeeper.e2e.ts`. Its settings and audit trail are its own tables keyed like AFK's, not preferences. It never judges a card that grants authority (permission, trust, consent, secret input), and a judgement it cannot reach fails open: the card goes to the user as a normal one. The working mode (run to completion, or check in with me) lives in the same crate: the app's mode is the user-only preference `workingMode` (check in when missing), a board's own is the `board_working_modes` table, and `workmode_get` / `workmode_set` are window-only ops, so no agent tool changes it. Every launch carries the mode in the `workmode` section of the prompt addendum. While a chat runs to completion, `stops.rs` holds a clean turn end that reads like a stop, asks the same helper to classify it, and either nudges the chat on (a message from Helm, never the user's words; at most three per run, never the same question twice) or lets it stop and flags it; the pure table is `stoproute.rs`, and a judgement it cannot reach lets the turn finish as it always did. Its bindings (`WorkModeView` and friends) regenerate with the same command |
| Repositories + worktrees (`host/crates/{worktrees,gitshim}`, `host/crates/projects/src/{repos,repo_ops,guard}.rs`, `ui/src/settings/runtime`) | as the Rust host and UI rows | `cargo test -p helm-worktrees -p helm-gitshim -p helm-projects` (the removal and stand-in tests need git on `PATH` and make real junctions in a temp folder); `node --test test/env-args.test.ts` in `worker/`. The git stand-in is the `helm-git` binary: the host copies it to `agent-bin/git.exe` in the profile and puts that folder first on a chat's `PATH` only while a repository has worktrees switched off; it is found beside `helm.exe` (or at `HELM_GIT_SHIM`), so the installer must carry `helm-git.exe` next to `helm.exe`. |
| Startup instructions + project line (`host/crates/projects/src/{startup,launch}.rs`, the startup seam in `host/crates/chats/src/{seams,submit,rollover}.rs`, `worker/src/drivers/claude/gates.ts`, `ui/src/sidebar`) | as the Rust host and UI rows | `cargo test -p helm-projects -p helm-chats` (regenerate `ui/src/api/generated/projects/` with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-projects bindings_are_current`, and the chats bindings the same way after a change to `ContextKind`); `node --test test/env-args.test.ts` in `worker/`; `node --test src/sidebar/*.test.ts` in `ui/`. An agent changes a project's startup instructions only through `app_project_startup`, which stages one Approve card (allow kind `project_startup`), never `app_update_project`. |
| Installer (`host/app/tauri.conf.json`, `host/app/windows/`) | `npm run build:installer` writes `target/release/bundle/nsis/Helm_<version>_x64-setup.exe` (per-user NSIS, no updater; built locally, not published). It bundles `worker/src` and every `helpers/<name>/src` as resources; a new helper must be added to `bundle.resources`. `bundle.windows.allowDowngrades` stays `true`, so a setup installs in place over a build with a higher version number. It also builds and carries `helm-git.exe` and `helm-launcher.exe` beside `helm.exe` (`host/app/tauri.installer.json`); its hooks end a running launcher before the template closes Helm, and the uninstaller ends it and removes its logon entry | `node --test e2e/w5-installer.e2e.ts` in `checks/` (what the bundle must carry); smoke from the INSTALLED app: install with `/S`, launch `Programs\Helm\helm.exe` with `HELM_PROFILE_DIR` set to a scratch folder, check the usage meter shows numbers, a new chat gets an automatic title and a chat round-trips; then uninstall (`uninstall.exe /S`; the profile stays) |
| Always-on launcher (`host/crates/launcher`, `--background` in `host/app/src/{main,shell}.rs`) | `cargo build -p helm-launcher` → `target/debug/helm-launcher.exe` (`npm run build:debug` does not build it) | `cargo test -p helm-launcher -p helm-app`; e2e R6 in `checks/e2e/w7-relay.e2e.ts` (needs the launcher built as well as the app and the hub). Tests use an in-memory `Run` key. A debug build never starts the launcher unless `HELM_TEST_LAUNCHER=1` and never writes the real `HKCU\...\Run` key unless `HELM_TEST_LAUNCHER_REGISTER=1`; run the launcher by hand only against a scratch profile (`helm-launcher.exe --profile <scratch>`). Its log is `diagnostics/launcher.log` in that profile and never holds the token |
| Local models (`host/crates/localmodels`, local parts of `host/crates/chats`, `host/crates/usage/src/{prices,summary}.rs`) | as the Rust host row | `cargo test -p helm-localmodels -p helm-chats -p helm-usage` (regenerate the bindings with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-localmodels bindings_are_current`). Tests use in-process fake servers on ephemeral ports and never contact a real Strata or Ollama; in debug builds `HELM_TEST_LOCAL_SERVERS` is `off` (no local server is contacted) or a loopback address every configured server uses instead. Helm asks a local server only for a catalogue refresh, a Test or a local chat's turn, never at start-up or on a timer |
| Declared waits + agent tools (`host/crates/waits`, `host/crates/usage/src/summary.rs`, `host/crates/chats/src/flags.rs`) | as the Rust host row | `cargo test -p helm-waits -p helm-usage`; `cargo test -p helm-chats flag_attention`. A wait's firing rules are one table in `waits/src/model.rs`; pull-request waits read through `gh`, which the tests replace with a fake |
| Web search (`host/crates/webtools`, `ui/src/settings/websearch`) | as the Rust host and UI rows | `cargo test -p helm-webtools` (a stand-in for Brave on a loopback port: the key, the tool, the Claude-chats switch and every refusal; no test reaches the real service). In debug builds `HELM_TEST_BRAVE_URL` points searches at a loopback address, nothing else. The key lives only in the credential store; no op, tool result, log line or error may carry it |
| Sealed pages (`host/crates/pages`, `host/crates/hosttools/src/pages.rs`, `ui/src/pages`) | as the Rust host and UI rows | `cargo test -p helm-pages` (sessions, the `helmpage` scheme, assets, the file watch, saved state and pins, over temp folders) and `cargo test -p helm-hosttools pages`; `node --test src/pages/*.test.ts` in `ui/` (the bridge rules and the sandbox string). A page runs in an iframe whose sandbox leaves out same-origin; the policy sent with it allows connections to `blob:` and `data:` only until the network switch is on for that open. Offline it also carries a `Connection-Allowlist` header, which closes WebRTC and the connections frames and navigations open (the policy covers neither); in a web view not known to enforce that header (`engine_seals_offline_scripts`), an offline page runs without scripts. Do not add `allow-same-origin` to the sandbox, widen `connect-src` or let an op take a path from a page: a session id fixes which file and which saved state a request touches |
| Profiles + devices (`host/crates/{profiles,devices}`, `host/crates/relay/src/devlink.rs`, `ui/src/{profiles,devices}`, `ui/src/settings/{profiles,devices}`) | as the Rust host and UI rows | `cargo test -p helm-profiles -p helm-devices` (regenerate `ui/src/api/generated/profiles/` with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-profiles bindings_are_current`; `devices/tests/two_hosts.rs` runs two installs through an in-memory hub: what a device of the same person, a household member and an unpaired PC may each do); `node --test src/profiles/*.test.ts src/devices/*.test.ts` in `ui/`. A request from another device is checked in `devices/src/serve.rs` against the person this PC is paired as; consent and Allow cards are never answered from another device |
| Knowledge layers + sync (`host/crates/skills`) | as the Rust host row | `cargo test -p helm-skills` (layers, rules, agents, memories and the hub sync over temp folders and a fake hub; nothing reaches a real hub). Regenerate `ui/src/api/generated/skills/` with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-skills bindings_are_current` |
| Voice on the PC (`host/crates/relay/src/voice*.rs`, `checks/voice-bench`) | as the Rust host row | `cargo test -p helm-relay`; `node --test e2e/voice-bench.e2e.ts` in `checks/` (the benchmark's prompts, fake hub and maths only). The benchmark itself (`checks/voice-bench/run.ts`) spends plan usage: it runs only by hand with `HELM_LIVE_CLAUDE=1`, never from `npm test` or the e2e run |
| Dictation (`host/crates/dictation`) | as the Rust host row | `cargo test -p helm-dictation` (a loopback stand-in for the speech-to-text server; no test sends audio anywhere else). Regenerate `ui/src/api/generated/dictation/` with `HELM_UPDATE_BINDINGS=1 cargo test -p helm-dictation bindings_are_current` |
| Desktop pet + celebrations (`host/app/src/pet.rs`, `host/app/capabilities/pet.json`, `ui/src/{pet,delight}`) | as the Tauri app and UI rows | `node --test src/pet/*.test.ts src/delight/*.test.ts` in `ui/`. The pet window gets only the capabilities in `pet.json` |
| Native toasts (`host/crates/platform/src/toast.rs`, `host/crates/shell/src/toasts.rs`) | as the Rust host row | `cargo test -p helm-platform -p helm-shell`; e2e `checks/e2e/w3-visual.e2e.ts` (V8 reads the toast probe, so no toast is shown during a check) |
| Full checkpoint (all of the above) | `npm ci` (CI does the same), then `cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && npm run build:debug` | `cargo test --workspace && npm run typecheck -w ui && npm test` (`npm test` runs every workspace's tests), then `npm run e2e -w checks` |
